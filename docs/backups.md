# Backup and restore process

Backups are a shared responsibility: Supabase protects the managed database according to the selected plan, while Le Yard must verify configuration, preserve private Storage objects, and rehearse recovery. The `backup_runs` table is an evidence registry; inserting a row does not create a backup.

## Required backup set

1. PostgreSQL database: schemas, Auth-linked application data, policies, and tenant records.
2. Private Storage: receipts, employee documents, chat attachments, closeouts, inventory evidence, SOPs, incidents, reports, imports, and checklist files.
3. Application configuration: reviewed migrations, deployment commit, and non-secret environment-variable names.
4. Secret inventory: credential owner and rotation date only. Never store raw secrets in backup evidence.

## Production policy decisions still required

Owners must approve:

- recovery point objective (acceptable data-loss window)
- recovery time objective (acceptable outage length)
- backup and evidence retention periods
- logical export cadence
- Storage manifest cadence
- encryption and off-platform copy requirements
- restore-test frequency and responsible person

The demo application deliberately labels these as not configured.

## Backup procedure

1. Confirm the Supabase project, environment, region, and backup/PITR settings in the platform console.
2. Confirm the latest managed database backup is healthy.
3. Generate an encrypted logical backup only through an approved, access-controlled runner when the policy requires one.
4. Generate a Storage manifest containing bucket, object path, version/etag when available, byte size, and checksum. Do not make a private bucket public to copy it.
5. Store backup artifacts in the approved encrypted destination with access independent from routine restaurant users.
6. Insert a `backup_runs` evidence record containing provider, backup type, status, timestamps, encrypted reference, and non-secret metadata.
7. Alert an Owner/Admin on failure; do not silently overwrite the last known-good evidence.

Never place a database password, Supabase secret key, signed file URL, or integration token in `backup_runs.metadata` or application logs.

## Restore drill

Perform drills in a disposable, isolated nonproduction project.

1. Obtain owner approval and choose a known backup point.
2. Create or identify an empty isolated restore target.
3. Restore the database according to the active Supabase plan/process.
4. Restore private Storage objects while preserving their tenant/location paths and private access.
5. apply any forward migrations newer than the restored point only after review
6. run database lint and the full RLS test suite
7. verify Auth/membership, signed file access, schedule, time clock, closeout/tips, inventory, CRM, reports, and audit immutability
8. confirm no email, push, Toast, Resy, payroll, accounting, or model integration can reach real recipients from the drill environment
9. measure recovery point and recovery time, then record `restore_tested_at` and evidence
10. destroy or archive the isolated target according to the approved policy

### Repository-controlled PostgreSQL drill

The repository includes a narrower database gate for proving that a supplied
logical archive is restorable without contacting Supabase, messaging, push,
Toast, Resy, payroll, accounting, or any other operational provider. It is a
database drill, not evidence that the platform backup or private Storage
payloads currently exist.

This is not a general-purpose verifier for untrusted external archives. The
accepted archive must be generated by the repository fixture command with the
same one-run secret later supplied to the verifier; authentication occurs
before `pg_restore` receives the bytes.

The verifier accepts only all of the following:

- a PostgreSQL custom-format archive whose first bytes and `pg_restore --list`
  catalog are valid;
- a separate strict JSON manifest bound to the archive filename, byte count,
  SHA-256, checked-out commit, complete ordered migration-bundle SHA-256, and
  exact migration head, plus the committed seed SHA-256 and normalized
  synthetic-data fingerprint. The complete manifest must authenticate with a
  one-run HMAC key created before fixture generation and never retained as
  evidence;
- the `isolated_synthetic_nonproduction` source classification, the committed
  `le-yard-demo-seed-v1` fixture contract, an explicit provider-disabled
  attestation, and an explicit statement that Storage payloads are not
  included;
- `BACKUP_RESTORE_CONTROL_DATABASE_URL` pointing to the exact `postgres`
  control database through `localhost`, `127.0.0.0/8`, or `::1`, using the
  `postgres` role, with no connection-string options;
- `BACKUP_RESTORE_PGDATA` naming the process-owned local PostgreSQL 17 data
  directory. Its live `postmaster.pid`, port, start time, `PG_VERSION`, and
  `pg_control` system identifier must match the connected server;
- a writable PostgreSQL 17 server that independently reports a loopback server
  address, has no other user database, role, relation, client session,
  replication slot, or subscription, plus PostgreSQL 17 `pg_dump` and
  `pg_restore` client tools.

Remote/SSH-tunneled, shared, production, wrong-database, wrong-role, non-PG17, standby, and
hash-mismatched inputs fail before any restore database is created. The script
never runs `supabase db reset`, never follows a linked Supabase project, and
never derives a target from application environment variables.

Use a newly initialized cluster dedicated to this one drill. A running local
Supabase stack or a developer cluster with any pre-existing application
database or role is intentionally rejected as shared state.

The local postmaster/PGDATA proof prevents a loopback-looking SSH tunnel from
being treated as a local disposable server. The process also holds a
cluster-wide advisory lease for its full lifetime. Every
database is created from `template0`, then attested as a fresh `public` plus
`plpgsql` catalog before migrations or restore; `template1` receives the same
fresh-catalog attestation. This rejects modified template user catalogs,
user-marked template databases, event triggers, concurrent drills, and other
client sessions rather than assuming the control database is enough.

For a local rehearsal against a dedicated loopback PG17 cluster:

```sh
export BACKUP_RESTORE_CONTROL_DATABASE_URL='postgres://postgres:postgres@127.0.0.1:5432/postgres'
export BACKUP_RESTORE_PGDATA='/absolute/path/to/this-drill-pgdata'
export BACKUP_RESTORE_PROVENANCE_KEY='<one-run 64-character lowercase hex secret>'
mkdir -p .restore-drill/evidence
npm run backup:restore-drill:create-fixture -- \
  --artifact .restore-drill/le-yard-synthetic.dump \
  --manifest .restore-drill/le-yard-synthetic.manifest.json
npm run backup:restore-drill:verify -- \
  --artifact .restore-drill/le-yard-synthetic.dump \
  --manifest .restore-drill/le-yard-synthetic.manifest.json \
  --evidence-directory .restore-drill/evidence
```

Use a new output directory for each run. The fixture command refuses to
overwrite either output and publishes private temporary bytes with an
exclusive no-clobber copy. The verifier copies the supplied archive and
manifest once into a mode-`0600` private directory, hashes/parses/restores only
those pinned copies, and rehashes them before evidence. Both commands create
UUID-named databases with a
fixed `le_yard_restore_*` prefix, close their pools, forcibly drop only those
validated names, and remove only cluster roles that the run itself created.

The verifier builds a second reference database from every current migration,
then proves the supplied restore has:

1. exactly the same migration history and head;
2. a byte-stable schema-only fingerprint for the approved application schemas;
3. the same complete public/private function grant catalog as current
   migrations, no anonymous execution, safe `SECURITY DEFINER` search paths,
   and no browser-executable trigger function;
4. RLS enabled and forced on every public table, including deny-all tables that
   intentionally have no policy, no effective anonymous relation or sequence
   privilege (including privileges inherited from `PUBLIC`), security-invoker
   public views, no public materialized views, and an exact reference-catalog
   fingerprint;
5. two independent migration-plus-seed builds produce the same all-table,
   all-sequence data fingerprint and a deliberate guest mutation changes that
   fingerprint. Seed-time values are represented as exact microsecond offsets
   from a fixed synthetic seed anchor, so the task due-at `+1 day` contract and
   other lifecycle relationships remain fingerprinted even though the wall
   clock is not. Bcrypt salts and generated Auth identity/notification IDs are
   canonicalized only after the exact demo password and stable relationship
   evidence are proved. Shift start/end times, stable UUIDs, entity
   relationships, audit IDs, row counts, and every other field remain
   fingerprinted;
6. only the reserved synthetic organizations, locations, identities, and
   `example.invalid` contacts, with exactly one phone-free guest, no separate
   contact claim, hold, or waitlist row; and
7. no integration connection or credential, queued integration job, enabled
   booking/messaging/push setting, reservation delivery, or connected-preview
   marker.

Success writes a mode-`0600` JSON evidence file without a connection string,
password, data row, or provider credential. Evidence includes the commit,
migration bundle/head, input manifest and archive hashes, archive-list hash,
authenticated manifest key ID (never the key), reference/restored schema hashes,
RLS and function-grant hashes, local postmaster/PGDATA system-ID hashes, PG17 version,
synthetic invariant counts, elapsed time, per-database/role/temp-file cleanup
disposition, a final empty-cluster attestation, and explicit
`false` values for provider contact, Storage verification, and platform-backup
availability. A cleanup or evidence-write failure fails the run.

Evidence output must be outside the checkout or inside a Git-ignored directory.
Evidence records the commit and hashed Git-visible worktree state both before
and after the drill, including each non-ignored untracked regular file's path,
mode, size, and content hash; untracked symlinks and special files fail closed. A technically successful
developer rehearsal from a dirty checkout proves the exact migration-bundle
hash but sets `repositoryControlledDatabaseGatePassed` to `false`; only a clean
unchanged checkout can produce repository-controlled release evidence.

The manual **Disposable PostgreSQL backup restore drill** GitHub workflow runs
this exact flow against a runner-local PostgreSQL 17 cluster bound only to
`127.0.0.1` and retains only the non-secret input manifest and evidence JSON for
30 days. It does not retain the synthetic database archive. Normal pull-request
CI keeps using the portable migration
checks; the native drill is deliberately manual because it is release
evidence, not a substitute for unit tests.

Supabase distinguishes physical and logical backups. Current managed projects
may use physical backups that are restored through the platform rather than
downloaded, while a logical export can be made with `supabase db dump` or
`pg_dump`. Supabase also states that database backups contain Storage metadata,
not the underlying private Storage objects. See the official
[Database Backups](https://supabase.com/docs/guides/platform/backups) and
[local CLI workflow](https://supabase.com/docs/guides/local-development/cli-workflows)
documentation. Therefore this repository gate cannot close the independent
platform/PITR availability, private Storage copy/restore, RPO/RTO, retention,
encryption, or production cutover gates.

## Emergency restore

An emergency restore needs joint Owner authorization when possible. Preserve the damaged environment and audit evidence, pause write-capable integrations, communicate the chosen recovery point, restore into a validated target, and switch traffic only after RLS and critical workflow checks pass.

Do not run destructive local commands against a linked project. Do not use the synthetic seed during a production recovery.
