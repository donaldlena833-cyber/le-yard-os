# Church Street Regulars

Daily Ritual v1 starts November 24, 2026, New York time. Three consecutive paid café days earns one croissant of the customer's choice; seven earns a surprise selected at the counter. One qualifying day per account per calendar day. Each milestone is earned once per contiguous streak; a gap starts a new streak, while previously earned treats remain claimable. Native Square spending points and their croissant reward are additional and separate. Apple Wallet displays native points, not daily streaks.

Square owns customer identity and purchase history. Operations derives days on demand from account-scoped ACCUMULATE_POINTS events, completed same-location orders and independently verified completed payments less refunds. It ignores manual points, canceled/unpaid orders, fully refunded orders, other locations and configured rehearsal-only variations. Missing orders, inaccessible payments, repeated pagination cursors or history exceeding the bounded read fail closed; the UI must not promise a treat from an incomplete check. No private customer reads occur in health probes.

Owners/admins in the verified live Church Street counter workspace can use `/loyalty` to check a member's daily ritual. The API requires a same-origin POST and validates the actor's session and location before using the service-only claim RPC. Public clients cannot submit qualifying purchase evidence or invoke the RPC. No names, phone numbers, card data or allergy information are copied into the claim ledger. Claims record the Square account identifier, qualifying order identifiers/dates, the actor and the treat handed over.

Counter procedure: identify the customer using Square; check the ritual; reserve the earned treat before preparation; add the actual treat to Square and apply the café's authorized comp; then record the selected item and confirm handoff. An unfulfilled reservation can be explicitly released. A reserved/fulfilled milestone blocks a second overlapping claim, including when late evidence extends or joins a streak. Handed-over records are immutable. A changed qualifying history appears for review and cannot be fulfilled automatically.

Runtime flag: `LE_YARD_REGULARS_STREAKS_ENABLED=true` in the production Operations project only, after migration `20261124051528_church_regulars_treat_claims.sql` is installed. Existing merchant/location configuration and read permissions remain required. Preview, Host and Phone cannot use production credentials for this feature.

Validation: focused tests cover calendar/DST boundaries, multiple same-day orders, gaps, earned treats retained across gaps, late evidence, refunds, provider scope, incomplete history, route authorization and recovery. The claim SQL is exercised in PGlite and an isolated PostgreSQL cluster, including simultaneous reservations. Full migration replay, generated database types, explicit function grants, lint, typecheck and production build are part of the release checks.

Physical acceptance still requires a real enrolled test customer, Register/reader check-in, verified purchase association, an iPhone Wallet pass, a chosen croissant recorded on the POS, one handoff and a repeat-attempt check. Fixture tests do not prove these device outcomes.
